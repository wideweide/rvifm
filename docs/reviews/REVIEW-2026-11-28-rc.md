## 1. 已经验证到位的改进

这一轮不是"文档改字"，代码确实动了。以下均经代码核查：

### 1.2 运维深度

### 1.3 工程与体验

- **质量债**：10 个模块的文件级 `#![allow(dead_code)]` 已清零；`AppError` 类型化开始落地。

这些工作值得肯定：它把上一版报告里"功能有但不够深"的部分补掉了大半。

### 2.1 CI 仍然不是绿的（supply-chain）

最新 run `46131729042`（HEAD `2727040`）的 job 结论：

|---|---|

| test (macos-latest) | **success** |
| test (windows-latest) | **success** |
| fuzz | in_progress |
| **supply-chain** | **failure（`cargo deny check`，exit 4）** |
| release / release-checksums | skipped |

**结论**：M90-1 的"修 Windows/macOS 测试"确实完成了——这是上一版最刺眼的问题，现已消失。但整条 main run 仍会以 failure 结束，因为 `cargo deny check` 失败。时间上与 M97 引入 `pulldown-cmark-mdcat`（MPL-2.0 AND Apache-2.0）及 Markdown 依赖树重合，具体命中项需要看 job 日志；无论原因是什么，**"main CI 绿"这条预期没有达成**。

另外，此前 08:12–08:16 的三个 run（8789689 / 777cc8c / d53a823）都是 failure；也就是说在一个时间窗内，main 连续红灯，直到 M90 的测试修复才把 test 面拉绿。

### 2.2 修复没有交付给任何用户

- 当前 HEAD 比 `v1.5.0` 领先 **77 个提交、50 个文件**；
- 没有 bump 版本、没有新 tag、没有新 Release（最新仍是 v1.5.0）；
- crates.io **仍是 1.0.0**（2026-11-22）。

这意味着 M89–M100 的所有改进——流式传输、异步目录、du/dup/checksum 深度、doctor、undolist、split/join、Markdown 预览、窄屏适配——**普通用户一项都拿不到**。README 顶部虽然加了"crates 版本滞后"提示，但快速开始仍写：

> `cargo install rvifm` 可直接安装发布版本

这与顶部提示直接矛盾；GUIDE 第 10 行给 `cargo install`，第 23 行才说"不是最新版"，对只看命令块的用户没有保护。

**判断**：这是本轮最大的"预期落差"——代码层完成了，交付层没有。

### 2.3 harness 门禁没有真正接入

`scripts/harness_check.py` 本身修得很好：

- 正则已改为单反斜杠，实测 R2 命中、R4 命中 10 个版本小节、R5 命中 3 条；
- R10（PLAN↔TASKS）、R11（发布事实）、R12（CI 结论）已实现；
- 注入 `RVIFM_MAIN_CI=failure` 时，脚本正确输出 `[R12-CI] ... 仍写「全绿」` 并以 1 退出。

但：

1. **`.github/` 下没有任何 workflow 调用 `harness_check.py`**，也没有 `RVIFM_MAIN_CI` 注入。R12 在真实 CI 中永远不会生效。
2. 脚本尾部仍打印"九条规则全部通过"，实际已 12 条，输出口径过期。
3. `STATE.md` 的"当前阶段"仍写 **M0–M85**（更新时间 11-27），而代码已到 M100；R1 只匹配"执行中"字样，抓不到"阶段上界过期"。

**判断**：门禁从"坏的"变成了"好的但没插电"。

### 2.4 100k 性能：目标达成，但测量口径变了，并带来排序回归

**好消息**：

- `lazy_attrs` 默认 true，`load_entries` 首屏跳过逐条 `metadata`；
- `fill_visible_attrs` 只补齐可见区；
- 新 bench：`load_100k` **450.97ms**（旧 6.83s），nightly bench 门禁 ±10%。

**但必须说清楚**：

1. 新 bench 测的是"首屏加载（无全量 stat）"，不是旧的"全量元数据路径"；6.83s → 450ms 不是同一件事的 15 倍优化，而是**换了一条更轻的路径**。
2. **排序正确性回归**：`apply_sort_multi` 直接对现有 `entries` 排序；`lazy_attrs` 下非可见条目的 `size` / `mtime` 都是 0，代码里没有任何"排序前补齐全部元数据"的步骤。因此在大目录里执行 `:sort size` / `:sort mtime` 或 `S` 对话框按大小/时间排序，会得到**错误顺序**（所有值相等，最后退化为按名称）。
3. 同理，`:sort size` 后状态栏会显示"已排序"，但结果不可信——这比慢更糟。

这是一个新引入的 P1 正确性缺陷，必须在下一次发布前修掉。

### 2.5 向导覆盖率没有达到 90%

- 向导现在 **14 模块 / 114 项**，窄屏也适配了，质量仍然很高；
- 但按 `:` 命令字面统计：exec 里 63 个命令，向导文本命中 **49 个 = 77.8%**；
- TASKS 里写的"55/59=93%"用的是更窄的分母（不含新增 Git/split 命令与部分子命令），口径与"全部命令"不一致。

更严重的是**可发现性**：

| 新命令 | help.txt | GUIDE | tutor |
|---|---|---|---|
| `:log` | 0 | 0 | 0 |
| `:blame` | 0 | 0 | 0 |
| `:stash` | 0 | 0 | 0 |
| `:branch` | 0 | 0 | 0 |
| `:split` | 0 | 0 | 0 |
| `:join` | 0 | 0 | 0 |
| `:undolist` | 0 | 0 | 0 |
| `rvifm doctor` | 0 | 0 | 0 |

这八项在 `exec.rs` / `main.rs` 里都有实现，但**帮助、手册、向导三处全部没有**。用户只能靠读源码或 CHANGELOG 发现它们；命令补全的描述来自 help.txt，因此这些命令连补全描述都不会有。

**判断**：向导本身是 A-，但"覆盖率 90%"不成立，且新功能处于"暗功能"状态。

### 2.6 队列仍在 UI 线程同步执行

`TransferState` 和队列 UI 都有了，但消费逻辑仍在主事件循环里：

```text
每次 event::poll 前 → 取队首 → 同步 upload_chunked / download_chunked → 再入队/完成
```

1GB 文件会在这一个 tick 里阻塞 UI，进度只能按条目更新，不能按字节刷新；M91-6 的"1GB + 断网三次 + 内存 <64MB"也被标为 deferred。**流式内存目标达成了，后台执行目标没有达成。**

## 3. 全面评估

### 3.1 稳定性

| 项 | 结论 |
|---|---|
| 生产 panic 面 | **0 unwrap / 0 expect / 0 panic**，2 处 `unreachable!`（方向映射守卫）；`allow(dead_code)` 已清零 |
| 数据安全 | 删除走暂存；Git hunk 丢弃默认关；传输 `.part` + 头哈希；向导沙箱不写 frecency |
| 自动化 | fuzz 五靶 + proptest 十属性 + cargo-deny/SBOM；但 supply-chain 当前红 |
| 跨平台 | test 三平台已绿；release 仅 musl 三归档（x64/aarch64/windows） |
| 遗留 | sftp 覆盖率 15.57% deferred；fuzz 24h deferred；app/tests.rs 16k 行未拆 |

**稳定性代码面：A-。工程面：B-（CI 红在 supply-chain，不是代码崩溃）。**

### 3.2 性能

| 场景 | 现状 | 评价 |
|---|---|---|
| 预览（文本/图片/PDF） | 异步 worker + mmap + SIMD + 编码缓存 | **A-**，同类领先 |
| 100k 目录首屏 | 450.97ms | **B+**，比旧版好一个量级 |
| 100k 按 size/mtime 排序 | 元数据未补齐，顺序错误 | **D**，新增回归 |
| 1GB 本地复制 | 1.79GB/s（旧基线） | A |
| 1GB SFTP | 流式已实现，真实 1GB 验收 deferred | B |
| `:du` / `:dup` / `:checksum` | 后台/分段/流式已改 | B+ |
| bench 门禁 | nightly，固定 450.97ms ±10% | B（单机基线，跨 runner 易抖） |

### 3.3 易用性

**做得好的**

- 首次启动自动进向导；无配置也能开始；
- 自动生成带注释的 `config.toml` + keymap/opener 示例；
- fzf 式 `:` 补全（M87）、命令历史只记成功、IME 自动切换；
- 方向键 / 鼠标 / vifm z 系列 / 命名标签 / 布局切换；
- `rvifm doctor` + panic hook，报障有入口；
- 向导 114 项、窄屏适配、沙箱真实操作。

**扣分项**

- 8 条新命令三处文档全缺，属于"暗功能"；
- README 安装段与顶部警告矛盾；
- 行为反复：M49 fixed-side → M52 反转；M73 焦点样式 → M80 重做 → M81 再调；`V` 键移除、单键 `g` 退役。1.x 内没有迁移别名，老用户会"手滑"；
- 排序回归会让用户觉得"排序坏了"，比"慢"更伤信任。

### 3.4 功能覆盖（对竞品）

v1.5 + M100 的覆盖面已经接近 TC/DC：

- **已原生到位**：双栏/多标签/命名标签、归档浏览/创建/解压、传输流式、冲突对话框、元数据保留、chmod、du/dup/checksum、hex/CSV/PDF/Markdown 预览、SFTP+ProxyJump+agent+指纹、UAC、git diff/stage/hunk、fzf 补全、IME、向导、doctor、split/join、undolist。
- **仍是简化**：队列后台化、sync 三策略之外的冲突处理、rar 浏览、缩略图网格、文件注释/ACL。
- **明确不做**：插件系统、归档内写、FUSE、内嵌视频。

**覆盖率判断**：功能类目约 90% 对齐 TC/DC；深度约 70%；"可发现 + 可安装 + 可验证"约 50%。

## 5. 下一步建议（M101–M104）

### M101 交付闭环（P0，2–4 天）

1. 修 `cargo deny check`（定位新依赖命中项；必要时在 `deny.toml` 加带理由豁免）。
2. 加 `harness_check` CI required job，注入 `RVIFM_MAIN_CI`；修脚本尾部"九条"文案。
3. 发布 **1.6.0**：包含 M86–M100；三平台 + 三归档 + SHA256SUMS；crates.io 若仍不发布，README/GUIDE 统一为"Release 安装"。
4. STATE 阶段更新到 M100；README 状态句同步；安装段与顶部提示统一。

### M102 排序正确性（P1，2–3 天）

1. `apply_sort_multi` 检测 `Size`/`Mtime` 且 `lazy_attrs` 时，先异步补齐全部元数据（带进度/可取消），再排序。
2. 补回归测试：1000 个大小随机文件，`:sort size` 结果严格有序。
3. bench 增加"全量 stat + 排序"基线，和首屏基线并列。

### M103 队列后台化（P1，3–5 天）

1. 传输 worker 线程 + 每 100ms 回传字节进度；UI 只消费事件。
2. 运行中暂停/取消真正生效；失败重试计数与退避。
3. 1GB + 断网三次 + 内存峰值 <64MB 实测回填。

### M104 可发现性收口（P1，2–3 天）

1. help.txt / GUIDE / 命令补全补齐 8 条新命令；
2. tutor 增加 Git 扩展、split/join、undolist、doctor 模块；覆盖率按"全部 `:` 命令"口径 ≥90%；
3. 行为变更政策落地：移除的 `V`/单键 `g` 给兼容别名与提示；CHANGELOG 增"行为变更"小节。

### 可选（M105+）

- 缩略图网格、rar 浏览、FTP/WebDAV（按需求）；
- `:branch` 切换 + worktree 管理；

- 英文界面/文档（向导是最佳传播载体）。
