## 1. 稳定性评估

### 1.1 代码面：这版本的硬功夫

用严格口径（剔除 `#[cfg(test)]` / `#[cfg(all(test, ...))]` 之后的生产代码）统计：

| 指标 | 数值 | 评价 |
|---|---|---|
| `.unwrap()` | **0** | 生产路径无 panic 诱因 |
| `.expect()` | **0** | 同上 |
| `panic!` | **0** | — |
| `unreachable!` | 2（`app/jobs.rs` 方向映射后守卫） | 可接受，属于穷举分支 |
| `unsafe` | 13（全部集中在 `privilege.rs` Windows FFI） | 有注释豁免，边界清晰 |
| `#![allow(dead_code)]` | 仍有 10 个模块文件级 | 唯一未还的旧债 |

配套的验证设施也已成型：`fuzz/` 五靶（zip / tar.gz / 7z / 路径规范化 / 反序列化）在 CI 绿；proptest 十属性（曾在 M40-3 抓到 `natural_cmp` 非全序导致 `std sort` panic 的真实缺陷）；`deny.toml` + cargo-audit + CycloneDX SBOM；RUSTSEC 豁免逐条附暴露面说明。

**结论：作为"不会随便崩"的文件管理器，1.5 是合格的。**

### 1.3 发布完整性（已修复，但仍有缺口）

| 项 | v1.0.0 | v1.5.0 | 证据 |

| tag CI | 失败（aarch64 腿） | **全绿**（run 45996577565） | GitHub API |
| 归档 | 缺 aarch64 | 3 个 musl 归档齐全 | Release 资产 |
| SHA256SUMS | **只有 Windows 1 行** | **3 行、与资产一一对应** | 实际下载校验 |
| 生成方式 | 各 job 互相覆盖 | 新增 `release-checksums` 汇总 job（`needs: release`） | `.github/workflows/ci.yml` 273-306 |

发布流水线本身已经修好；**唯一但很重的缺口是 crates.io**。`README.md:149` 与 `docs/GUIDE.md:10` 都写着 `cargo install rvifm`，而 cargo 装到的是 1.0.0——少了 1.1–1.5 的 IME 支持、预览越界修复、会话保存修复、tutor 105 项、`:diff`、mmap 虚拟化。用户按文档操作会拿到一个"看起来是最新、实际差 5 个版本"的二进制。

### 1.4 数据安全性

- 删除走应用内暂存（`:trash` + `clear` / `purge --before`），`DD` 永久删除有强提示。
- Git 写操作（`:diff` 内 stage / discard / hunk `D`）默认 `confirm_destructive = true`，hunk 丢弃走"预览确认 + `git apply -R` + `u` 恢复原文"，且标注为**实验性**。
- 传输有 `.part` + `.part.meta` 偏移现场与头哈希校验，完成原子 rename。
- 向导沙箱（M67）在 `/tmp/rvifm-tutor` 内做真实操作，不写 frecency、保留撤销栈——这一点设计得很好，避免了"教学误导用户删真实文件"。

风险点：`:sync --delete` 直接删除目标多余项（虽 `--delete` 需显式给），建议在 `--apply` 之前强制列出删除清单并要求二次确认；Git hunk 级丢弃建议默认关闭或加 `--experimental` 开关，因为反向 apply 在有未保存工作区时破坏性很强。

## 2. 高性能评估

### 2.1 真正做对的：预览与渲染栈

M60–M62、M83、M85 把预览这条链路彻底重做了，这是本次复核最大的技术亮点：

| 改造 | 做法 | 效果 |
|---|---|---|
| 真异步预览 | worker + generation，文本读取 / hex 判定 / 图片解码 / Office / 归档 / PDF 文本全部离 UI 线程 | 预览不再拖慢按键响应 |
| 大文本虚拟化 | `memmap2` 视口读取（1MiB 阈值）+ 每 1024 行偏移检查点 | 打开几百 MB 文本不再整文件读入 |
| 文本预览两段式消除 | 始终视口渲染 + 始终高亮，缓存 key 含 mtime/size | 不再有"先截断再刷新"的闪烁 |
| 图片流水线 | `fast_image_resize` SIMD 预缩放（最长边 1600）+ `ThreadProtocol` 后台编码 + 已编码缓存 | UI 线程不再每帧重复编码 |
| 递归扫描 | `O` 后台流式扫描（深度 20 / 5 万条护栏）+ 实时过滤 + Esc 停线程 | 大目录树搜索不冻结 |

### 2.2 仍然卡住的：目录加载与运维命令

```text
tab.rs:2249  load_entries()  →  std::fs::read_dir + 每条 entry.metadata()
             ↑ 在 UI 线程同步调用（refresh / 导航 / 外部变更监听都走它）
```

项目自己的 `docs/bench.md`（2026-11-21，未随 1.5 复跑）给出的数字仍然挂着：

| 基准 | 结果 | 目标（上一版建议） |
|---|---|---|
| `load_100k/load_entries_100k` | **6.83 s**（≈68 µs/条目） | < 300 ms |
| `natural_sort/sort_10k_natural` | 3.26 ms | 达标 |
| `frecency_replay/replay_100k_events` | 65 ms | 达标 |
| `copy_1gb/copy_file_chunked_1gb` | 570 ms（1.79 GB/s） | 达标 |

也就是说：**预览变快了三倍十倍，但进入一个 10 万文件的目录，界面依然要冻住约 7 秒**。而且外部变更监听会再次触发同一同步路径，一次 `git checkout` 大目录就可能连卡几次。

其他同步阻塞点（均在 UI 线程直接执行）：

| 位置 | 问题 |
|---|---|
| `exec.rs:2917` `:du` | 顺序遍历 + 逐条 `metadata`，10k 上限，无取消，结果只是 top-5 文本 |
| `exec.rs:2969` `:dup` | 注释写"size 分组 → 全文 SHA-256"，实现是**对每个文件整文件 `fs::read` 后哈希**，无 size 预筛、无头部哈希 |
| `exec.rs:3024` `:checksum` | 整文件读入、只支持 md5、只生成 sidecar（无校验模式） |
| `exec.rs:3178` `:extract` | 逐成员同步解压，SPEC 要求的 job 化未做 |
| `app/mod.rs:1100` 队列消费 | 只在队首为 Upload 时、每次 poll **同步执行一次 `upload_chunked`**；且 `upload_chunked` 第一步是 `std::fs::read(src)` 整文件读 |

### 2.3 传输：偏移续传有了，流式没有

| 能力 | 现状 | 评价 |
|---|---|---|
| 偏移续传 | `.part.meta`（offset / total / src mtime / 头 4KB 哈希）+ `write_range` 续写 | 真实现，可用 |
| 内存 | 上传前 `fs::read` 整个源文件；下载 `be.read` 返回 `Vec<u8>` | **1GB 文件 = 1GB 内存**，流式未做 |
| 状态机 | 只有 `TransferDirection` 枚举，没有 Pending/Running/Paused/Done/Failed/Cancelled | M36-4 仍未落地 |
| 队列 | 仅 Upload；无暂停/恢复/重试；无进度显示；`x` 只移除未开始条目 | M36-7 仍是骨架 |
| 冲突确认 | M86-8 已做对话框（同路径 3 项 / 异路径 6 项、j/k 选择） | **1.0 的"ask 即报错"已修好** |

## 3. 导师模式（`:tutor`）可用性

这是 rvifm 相对 vifm / ranger / yazi / TC / DC 最独特的能力——这些工具都没有内建交互式操作向导。

### 3.1 实现面

| 要素 | 实现 | 证据 |
|---|---|---|
| 内容 | 14 模块 / **105 条目**（TOML 内嵌，`assets/tutor/*.toml`） | 逐文件 `[[items]]` 计数 |
| 触发 | 首次无配置启动自动进入；`:tutor` 随时重进；Ctrl+Q 重进提示 | `app/mod.rs:772` `first_run = !config_path().exists()` |
| 练习环境 | 沙箱 `/tmp/rvifm-tutor/{left,right}` + 5 个样例文件，真实操作但不写 frecency、撤销栈保留 | `tutor.rs:138-183` |
| 进度 | `tutor_progress.toml` 持久化、损坏静默降级、未知 ID 裁剪、`:tutor reset <模块>` | `tutor.rs:276-359` |

### 3.2 覆盖率

按命令面板（`src/app/exec.rs` 的 56 个 `:` 命令）比对：

| 口径 | 数量 | 比例 |
|---|---|---|
| 向导中直接出现的命令 | 40 / 56 | **71%** |
| 未覆盖的主命令 | `:view`、`:grep`、`:link`、`:gitui`、`:goto`、`:frecency`（含 `stats` / `export` / `purge` / `prune`） | — |
| 属对话框内按键、非独立命令 | `asc` / `desc` / `left` / `right` / `clear` / `confirm` | 可不计入缺口 |
| 动作层（`Action` 枚举） | 51 个动作，默认键位与 z 系列、方向键、鼠标均已入对应模块 | 键位覆盖良好 |

**判断**：向导覆盖的是"日常主干"（导航、选择、批量、归档、frecency 跳转、Git、队列、同步、校验），质量很高；缺口集中在**进阶/管理类命令**（`:frecency` 数据管理、`:grep` 内容检索、`:view` 查看器语义、`:link`、`:goto` 偏移跳转），以及 1.1 之后新增的 Git `:diff` 写操作细节。

### 3.3 可用性上的三个改进机会

1. **从"教程"升级为"能力认证"**：完成指定模块后解锁提示（例如完成 `file_ops` + `visual_tag` 才允许在真实目录做 `:sync --delete`），或至少给出"该命令你还没学过"的软提示。文件管理器是最容易"误操作即丢数据"的工具，向导与破坏性操作之间存在天然的联动价值。
2. **缺口补齐 + 覆盖率门禁**：把上面 6 个命令族补进 `maintenance` / `search_filter` 模块，并在 `harness_check` 增加"命令覆盖率 ≥ 90%"的规则（用 exec 命令表 × tutor 文本做集合差）。
3. **可发现性**：`requires` 环境项、模块总条目数、境界含义目前主要写在面板里；建议在 GUIDE 增加"按角色的 5 分钟路线"（运维排障 / 开发者 Git / 新手），并给 `:tutor` 加 `--role` 直接生成路径。

## 4. harness 体检：门禁失效 + 状态矛盾

### 4.1 三条规则实际上永远不会触发

`scripts/harness_check.py` 在仓库里跑是 `OK（九条规则全部通过）`。但把它的正则抠出来实测：

| 规则 | 代码里的正则 | 实测命中 | 后果 |
|---|---|---|---|
| R2 AGENTS/STATE 版本一致 | `(0\\.\d+\\.\d+) 已发布` | **0**（STATE、AGENTS 都不匹配） | 版本漂移永不被发现；且模式写死 `0.x`，而现在是 1.x |
| R4 PLAN 版本小节与正文 | `^### (0\d?\\.\d+\\.\d+)(（[^）]*）)\n` | **0**（PLAN 实际有 1.0.0–1.5.0 六个小节） | 发布状态自相矛盾不会被拦 |

### 4.3 建议的 harness 2.0

1. **修脚本本身**：正则改单反斜杠；R2/R4 的版本模式改为 `[0-9]+\.[0-9]+\.[0-9]+`；R6 去掉 `break` 并改为"扫描 STATE 全文中所有 `N 单测`"；R1 的批次头匹配放宽到"任何 `^## (M\d+|FIX-\d+|REL-\d+)` 段落 + 段内未勾数"。
2. **加三条硬规则**：
   - **R10 一致性**：PLAN 批次行状态必须与 TASKS 未勾数一致；
   - **R11 发布事实**：GitHub Release 资产集合 = CI 矩阵集合，`SHA256SUMS.txt` 行数 = 归档数，crates.io `max_version` = `Cargo.toml` 版本（若策略是"不发 crates"，则 README/GUIDE 必须显式写明"cargo 安装版本为 X，最新功能请下载 Release"）；
   - **R12 CI 事实**：`main` 最近一次 run 结论必须为 success，否则 README/STATE 不得出现"全绿"字样。
3. **把"全门禁绿"改成三态措辞**：`本机 Linux 绿` / `CI 三平台绿` / `tag 发布绿`，避免 M82–M88 这种"批次记录全绿但 main 红灯"的记录方式。
4. **覆盖率口径统一**：文档中一律写 `689 单元 + 14 集成（含 4 项 pdf-visual 门控）`。

## 9. 结论

v1.0 → v1.5 这六天，rvifm 做对了两件很难的事：一是把**预览与渲染栈真正异步化**（mmap 视口、SIMD 预缩放、后台编码），二是把**上手成本压到同类工具最低**（沙箱化向导 + 自动生成配置 + fzf 式补全 + IME）。生产代码零 `unwrap`、零 `panic`、fuzz/proptest/deny 齐备，Git 集成甚至做到了 hunk 级操作——这在同类 TUI 文件管理器里几乎没有对手。

但它现在的问题不在代码能力，而在**可信度**：

1. HEAD 的 main CI 是红的，Windows / macOS 已连红 6 次，而批次记录写着"全门禁绿"；
2. crates.io 停在 1.0.0，README 还在引导 `cargo install`；
3. 一致性门禁因为正则写错而"永远 OK"，掩盖了 450 vs 689、M86 待执行 vs 已完成这类矛盾；
4. 最影响日常手感的那条曲线——10 万文件目录 6.83 秒冻结——六天没有被改善，也没有被复测。

如果只做三件事：

1. **一周内做完 M89**：三平台 CI 绿、发布口径回真、harness 规则修好并新增 R10–R12。这不是加分项，是让别人敢用敢装的前提。
