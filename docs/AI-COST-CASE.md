# AI-COST-CASE

> 本文记录 rvifm 开发过程中的大模型 token 消耗，作为“AI 辅助开发大型 Rust 项目”的成本案例。
> 数据为估算与回忆，非精确账单；仅用于量级参考，不构成对任何模型的评价。

## 预估 vs 实际

| 阶段 | 预估 | 实际（至少） | 偏差 |
|---|---|---|---|
| 0.1.0 之前（M0–M6 核心闭环） | 1 亿 | 未单独统计 | — |
| 至 1.0.0（M0–M40 + AUDIT） | 1 亿 | **约 30 亿** | **约 30 倍** |

“1 亿”的预估基于“以官方文档为规格、允许简化”的路径，假设代码生成和调试各占一半。实际消耗远超预估，主要来自以下几个方面。

## 偏差来源

**① 需求描述的反复校对**
早期为了“把免费额度用满”而铺任务量，导致需求描述偏粗。后续用 DeepSeek 网页版校对、补全边界条件，这部分往返本身消耗了大量 token，且没有计入最初的预估。

**② 文档漂移的修复成本**
进度信息分散在多个 harness 文档中，漂移后需要多轮审计和修正。DeepSeek、千问、GLM 各自审计过一轮，每次审计都是一次完整的文档读取 + 比对 + 修改循环。

**③ 测试与验收的往返**
功能增多后，人工验收清单的生成、执行、反馈、修复形成长循环。测试失败后的定位和修复，往往比首次实现更耗 token。

**④ 平台特定代码的 CI 往返**
Windows 本地 clippy 看不到 `#[cfg(unix)]` 路径，问题在 CI 的 Linux job 才暴露。这类“本地绿、CI 红”的往返，每次都要重新读取错误、定位、修复、推送。

**⑤ 模型切换与上下文重建**
免费额度到期后的模型切换，需要重新建立项目上下文，这部分成本在预估中完全没有体现。

## 对“AI 辅助开发”的启示

- **“1 亿 token 能写完一个中型项目”是一个过于乐观的量级**。对于 10 万行级别的 Rust 项目，即使有完整的 harness 文档，实际消耗也可能在 10 亿–30 亿量级。
- **需求校对的投入应该前置**。早期把边界条件写清楚，比后期反复修复便宜得多。
- **文档职责必须单一**。进度锚点只保留一个，其余文档引用而非复制，能显著降低漂移修复成本。
- **CI 的跨平台覆盖要尽早**。本地看不到的代码路径，最终都会在 CI 上以“返工”的形式收费。

## 数据说明

本文的 token 数为量级估算，基于对话轮次、文档规模、代码增量的回忆统计，未接入精确的 API 账单。如果后续引入自动化的 token 记录机制，会更新此表。
