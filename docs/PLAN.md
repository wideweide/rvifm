# PLAN — rvifm 里程碑计划

本文件只回答“分几阶段、每阶段目标、依赖关系、何时发布”。单次提交粒度的任务见 [TASKS.md](TASKS.md)，验收标准见 [ACCEPTANCE.md](ACCEPTANCE.md)。

## 1. 总体策略

- 采用 **harness 模式**：文档是契约，Agent 每轮只做一个小任务，更新状态并提交。
- **M0–M6 构成 v0.1.0 核心版本**：可日常使用的浏览、文件操作、撤销、选择、搜索、配置、帮助。
- **M7–M11 是 v0.1.0 之后的增强**：归档浏览、frecency、图标主题、声明式键位、预览与打开。
- 优先级：`M0–M2` 必须闭环，尤其是 `u` 撤销；M3–M11 可以简化，但不得跳过文档更新。
- 每个阶段结束必须产出可运行版本、通过质量门禁、更新 `PLAN.md` 状态。

## 3. 阶段依赖说明

- **M1 必须包含多标签**：每个 tab 持有独立的 `Location`、光标、滚动、搜索状态。晚加会导致 M2 撤销、M4 搜索、M7 归档浏览全部回头改“当前 tab 上下文”。
- **M2 必须在 M1 之后**：撤销栈依赖稳定的 `Tab` / `AppState` 结构；撤销栈全局共享，`UndoableOp` 记录 tab 标识。
- **M3 依赖 M2**：批量操作复用单文件操作与撤销逻辑；tag 状态在批量操作后清空。
- **M4 依赖 M1**：搜索/过滤作用于当前视图；marks 不实现，路径跳转由 M8 的 `pick` 覆盖。
- **M5 依赖 M1–M4**：配置与最小命令模式建立在已稳定的导航、操作、搜索之上；键位覆盖推迟到 M10。
- **M6 依赖 M0–M5**：发布门禁需要完整核心功能与双平台 CI。
- **M7 依赖 M1、M4**：归档导航复用 `Location` 与搜索链路；不依赖配置系统。
- **M8 依赖 M1、M7**：`pick` / TUI 共用导航与预览；预览抽象在 M8 抽出，M11 扩展图片/Office/PDF。
- **M9 依赖 M1、M7、M8**：文件列表、归档浏览、pick 预览共享同一套图标/主题渲染。
- **M10 依赖 M1–M5**：动作层覆盖导航、文件操作、选择、搜索、命令模式。
- **M11 依赖 M7–M10**：预览覆盖物理目录、归档、pick；opener 分层与 M10 键位分层同构。

## 4. 发布划分

### v0.1.0（M0–M6）

交付标准：

- 能完成日常浏览、多标签、选择、复制、移动、删除、重命名。
- `u` 撤销可用，覆盖核心可逆操作，跨 tab 正确回滚。
- 有基础搜索、tag 批量操作、TOML 配置、最小命令模式、帮助页。
- 代码结构清晰，`cargo fmt` / `clippy -D warnings` / `build` / `test` 通过。
- CI 在 Linux + Windows 全绿，Release 产出两端可执行文件。
- README 明确声明“参考 vifm，非严格兼容”。

### 后续版本（M7–M11）

- M7 归档浏览、M8 frecency、M9 图标主题、M10 声明式键位、M11 预览与打开。
- 每个里程碑独立可发布；不要求一次性完成全部增强。
- 若预算或时间受限，优先完成 M7 与 M8（用户价值最高），M9–M11 可延后。

## 5. 预算与风险

### Token 预算

会话中的估算经过多次叠加，最终规划区间为 **约 7500 万–1.1 亿 token**，仅作为数量级参考，不是硬性上限。

| 范围 | 估算 |
|---|---|
| M0–M2 核心闭环 | 控制在 5000 万以内 |
| M7 归档浏览 | 增加 500 万–1500 万 |
| M8 frecency | 增加 400 万–1200 万 |
| M11 预览与打开（含文档预览） | 增加 500 万–1300 万 |
| 合计 | 约 7500 万–1.1 亿 |

控制手段：

- 每轮只注入当前任务相关 SPEC 片段，不通读全文。
- 每轮只做一个任务，避免上下文膨胀和半成品堆积。
- 同一任务 3 轮不过验收就缩小范围并 `deferred`。
- 接近预算上限时，优先保证 M0–M2 完整，M3–M11 简化。

### 主要风险

| 风险 | 缓解 |
|---|---|
| `u` 撤销的跨 tab、不可逆边界复杂 | M2 单独验收，删除走可恢复路径，必要时缩小到核心可逆操作 |
| 归档格式边界多（损坏、加密、超大索引） | 先支持 zip/tar/tar.gz，7z/rar 明确不支持；错误处理纳入验收 |
| `skim` 库 API 不稳定 | 3 轮不达标降级为 `nucleo` + 自绘 picker |
| `keymap-rs` 不满足多键序列/模式 | 降级为 `keybindings` crate 或自写轻量 Trie |
| `redb` 多进程并发 | 短事务 + 重试 + `events.pending` 降级；评分只在读时重放 |
| 图片协议碎片化 | `ratatui-image` 探测 + halfblocks 无条件兜底，不为终端写分支 |
| `exprim =0.4.0` 供应链风险（发布首日、零采用、主 crate 无 CI） | 仅作非默认 `pdf-visual` feature；固定 `=0.4.0` + `Cargo.lock` 入库；按 NOTES.md §4.8 条件观察 4–8 周后复评转正 |
| Win2016 上 ZCode 可能无法启动 | 改用 VS Code + `rust-analyzer` 或纯命令行；不影响项目内容 |
| CI 无 TTY 导致 TUI 测试失败 | 使用 `TestBackend`，冒烟只跑 `--version` / `--help` |
