# JOURNEY

> 本文是个人随笔，不属于项目规格或 harness 文档。
> 内容仅代表作者个人观点，不构成对任何工具/模型的评价建议。

## 为什么喜欢 Vim

第一次被 Vim 打动，不是因为“快”，而是因为**操作是组合的**。`d` 是动作，`w` 是范围，`dw` 是“删除一个词”；`y` 是取，`yy` 是“复制当前行”，`p` 是“粘贴”。这套“动词 + 名词”的组合逻辑，让记忆负担从“记住一百个快捷键”变成“记住几个动词和几个范围”。

但更深一层的原因，是**不同模式可以定义不同的快捷键**。同样是 `j`，在 Normal 模式是“下移一行”，在 Insert 模式就是输入字符 `j`。这种“模式隔离”让每个模式里的键位都可以被充分利用，而不必为了避让输入而牺牲操作的直接性。后来做文件管理器，最想保留的就是这一点：不是把 Vim 的按键抄一遍，而是保留“操作可以被组合、可以被预期、不同上下文有不同语义”的感觉。`yy` 之后 `p` 是复制、`P` 是移动，这种语义一致性比单个键位是否对齐更重要。

## Vim 模式在不同应用中的体验

用过的 Vim 风格工具大致分四类，每一类都让我更确信“Vim 模式不该只属于编辑器”。

**浏览器**：最早用的是 Vimperator，后来转到它的派生分支 Pentadactyl。Pentadactyl 在 Firefox 47 之后很多特性就不能用了，但那段“用 `f` 直接跳转链接、用 `:` 打开命令”的体验，让我再也不想回到纯鼠标浏览。后来换到 Tridactyl，虽然生态变了，但“键盘优先”的内核还在。

**文件管理器**：在 Windows 时代，我最依赖的是 Total Commander 的双栏模式，配合 VimDesktop（前身是 ViATc）给 TC 加上 Vim 热键——`h/j/k/l` 移动、更多组合操作，而且**不与 TC 自带快捷键冲突**。那是我第一次感觉到“双栏 + Vim 键位”可以同时成立。

**主流系统切到 Linux 后**，Total Commander 用不了了，改用 Double Commander，但它对 Vim 模式的支持始终不够“原生”。在寻找 Vim 模式支持的过程中发现了 vifm——它提供的不是“模仿 Vim 的按键”，而是完整的 Vim-like 环境：模式、选项、寄存器、命令行、映射，几乎是一套完整的 Vim 操作范式搬进了文件管理器。从那以后就深度用下来了。

**IDE/桌面环境**：IDE 的 Vim 插件通常只覆盖编辑区，文件树、终端、调试面板仍然是鼠标逻辑；桌面环境的 Vim 键位则各家取舍不一。共同点是——一旦习惯了组合语义，回到纯鼠标就会觉得“每一步都在做无用功”。

## 从 Total Commander 到 vifm，再到 frecency

vifm 本身已经提供了 **bmarks（bookmark）**：用户可以用关键词标记目录或文件，之后按关键词搜索并跳转。这部分能力并不缺，关键词书签也有自己的价值——它是“显式、精确、手动”的：我知道某个项目该叫什么名字，就给它一个关键词。

但 vifm **缺的是全局的历史导航记录，尤其是文件打开记录**。它的目录历史是视图级作用于当前 view 的历史，不是全局的。更重要的是，vifm **没有记录文件打开的历史**，也没有**频率**——它无法回答“我最常打开哪些文件”“哪些目录在最近一段时间里被反复访问”。

这三个缺口——**全局、文件打开记录、频率排序**——合起来就是“frecency”要解决的问题。

为此写了一个辅助插件：[wideweide/frecency](https://github.com/wideweide/frecency)。它是一个 navigation-history manager，用 **bash + SQLite + fzf** 实现真正的 frecency 评分（event clock + exponential moving sum），同时跟踪目录和文件，支持关键词书签、多词匹配、匹配质量分级，可以在 vifm、fish、bash、Neovim 里用，也可以作为独立 CLI。

它在 vifm 里工作得很好，但依赖链很长：SQLite（还要带 `SQLITE_ENABLE_MATH_FUNCTIONS`）、fzf（版本有要求）、bash 4.4+、`file`、`flock`，再加上一堆可选的预览工具。**换一台机器，就要重新配一遍环境**。

## 为什么用 Rust 重写

大模型辅助开发让“重写”这件事的门槛显著降低了。以前面对一个 17 万行 C 的项目，第一反应是“投入产出比不划算”；现在可以先以文档为规格、允许简化、分阶段交付，先跑通核心链路，再逐步叠加。

于是有了 `rvifm`：不是 vifm 的 fork，也不追求行为级兼容，而是**把 vifm 需要“装插件、配外部工具、写脚本”才能得到的能力，变成编译进二进制的默认行为**。frecency 从“bash + SQLite + fzf”变成“redb + 原生 picker”，归档浏览从“FUSE 挂载”变成“内置只读 VFS”，图标和主题从“装字体 + 装插件 + 改配置”变成“编译期集成”。

这件事在几年前大概不会开始。**是大模型把“重写”从一件需要立项评估的事，变成了一件可以边写边评估的事。**

## 用大模型开发 rvifm 的体验

### 前期策略与教训

项目启动时的想法很朴素：**尽量把任务量铺满，把晚间的免费额度用足**。这导致早期需求描述偏粗，一些边界条件没有想清楚就交给了模型。后来用 DeepSeek 网页版做了一轮校对和补全，但“实施后细节不尽如人意”的问题仍然存在——**校对了需求，不等于校对了实现**。

一个具体的教训是：需求文档写得“看起来完整”和“模型能无歧义执行”是两件事。前者是给人看的，后者需要把前置条件、失败路径、验收方式都写死。

### 文档漂移

harness 模式下，进度信息散落在 `STATE.md`、`TASKS.md`、`PLAN.md`、`NOTES.md` 多个文档里，漂移几乎是必然的。过程中用 DeepSeek 和千问做过审计，都指出了这个问题；后来让 GLM 5.3 Flash 自己审计自己，它也发现了同样的漂移。

这让人很难判断：**是模型不够给力，还是 harness 规则设计有问题？** 我的判断是后者占比更大。`STATE.md` 中途做过一次变更——从“记录历史信息”改为“只记当前状态和下一步”——这次变更是对的，但它也说明早期的文档职责划分不够清晰。**进度锚点应该只有一个，其余文档通过引用而不是复制来关联它。**

### 模型选择

前期计划全部使用免费模型。GLM 5.3 Flash 每晚赠送 1 亿 token，截至 1.0 版本，基本完成了所有规划功能。免费额度到期后，后续开发需要重新评估模型组合。

### 测试的麻烦与“导师模式”的诞生

到 1.0 时，功能已经很多，测试变成了一件很麻烦的事。让大模型导出人工校对清单，一边看一边记，仍然觉得繁琐。于是想到：**能不能把“测试”和“学习”做成同一套交互？**

新用户可以用它按顺序了解全部功能；维护者可以用它按顺序跑一遍人工验收；每一条都有“通过/未通过”或“掌握/未掌握”的判定，结果持久化，下次只看没过的。这个想法后来被称为“导师模式”——它既是教学工具，也是测试工具。类似的产品设计在文件管理器里还没怎么见过，做出来应该会挺有趣。

## Token 消耗

详见 [`AI-COST-CASE.md`](AI-COST-CASE.md)。一个提前的结论：**“1 亿 token 能写完一个中型项目”是一个过于乐观的量级**。到 1.0 时，实际消耗已经是这个预估的数十倍。偏差主要来自需求校对的往返、文档漂移的修复、测试验收的循环，以及平台特定代码的 CI 返工。
